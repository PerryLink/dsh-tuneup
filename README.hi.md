# dsh-clinic

**एक ही बार में DSH प्लगइन को स्वीकार करें — पैकेज संरचना, कॉर्डिस अनुबंध, सैंडबॉक्स बूट और डायरेक्टरी सूचियाँ।**

DeepSeek Harness प्लगइनों के लिए शून्य-निर्भरता वाला «अखंडता + रनटाइम स्वास्थ्य» परीक्षक: दोनों स्टैटिक परतें ऑफ़लाइन चलती हैं, डायनामिक स्मोक एक बार इस्तेमाल होने वाले सैंडबॉक्स में कंपोज़िशन बूट करता है, और निर्णय निकास कोड से पढ़ा जा सकता है।

## यह क्या है

`dsh-clinic` «क्या यह प्लगइन इंस्टॉल हो सकता है, बूट हो सकता है, कोई डायरेक्टरी इसे अस्वीकार करेगी?» को चार पठनीय परतों में बाँटता है: **R पैकेज संरचना → K कॉर्डिस अनुबंध → D सैंडबॉक्स स्मोक → CC डायरेक्टरी सूचियाँ**। R और K केवल कमिट किए गए ट्री को पढ़ते हैं — कोई निर्भरता इंस्टॉल नहीं, कोई नेटवर्क नहीं; D वास्तव में `npm pack` चलाता है और बिना कुंजी वाले प्रोफ़ाइल को एक बार इस्तेमाल होने वाले सैंडबॉक्स में मॉडल अनुरोध तक बूट करता है; CC पारिस्थितिकी के पाँच डायरेक्टरी/रजिस्ट्री की वास्तविक बाधाओं से मिलान करता है। एक रन छह-अवस्था वाला निर्णय (pass / warn / info / skip / fail / error) और सात निकास कोड देता है, इसलिए CI सीधे कोड पर शाखा कर सकती है।

मानदंड अनुमान से नहीं बने: वे 2026-09-07 की तीन प्रथम-स्रोत शोध पंक्तियों से आते हैं — deepseek-harness का दस्तावेज़ और स्रोत, cordiverse/cordis के स्रोत-अनुबंध, और वर्कस्पेस के हर वितरण चैनल की सूची (पूरा पाठ और हर मानदंड का स्रोत [`SURVEY.md`](SURVEY.md) में)। यह परीक्षणों का विकल्प नहीं है और सुरक्षा ऑडिट नहीं है: जो स्टैटिक रूप से तय हो सकता है, उसे यह पुनरुत्पाद्य गेट बना देता है।

**📖 पारिस्थितिकी ज्ञानकोश** (मापे गए आँकड़े, विपणन नहीं): [प्लगइन विकास गाइड · चयन के आँकड़े · रखरखाव के मानदंड](https://perrylink.github.io/dsh-plugin-guide/)।

### नाम की टकराहट (महत्वपूर्ण)

2026-11 में यह रिपॉज़िटरी **`@perrylink/dsh-plugin-doctor`** से **`dsh-clinic`** हो गई; पुराना स्कोप्ड npm पैकेज और पुराना GitHub रेपो पॉइंटर/बैकअप के रूप में बने हुए हैं। पारिस्थितिकी में इसी नाम के अन्य प्रोजेक्ट भी हैं — गलत वाला इंस्टॉल न करें:

- npm का सादा नाम **`dsh-plugin-doctor`** (0.1.1) **Xrainsmile/DSH-Plugin-Doctor** का है, इस रेपो का नहीं। **कभी `npx dsh-plugin-doctor` न चलाएँ** — वह किसी और का पैकेज चलाता है।
- इस रेपो का npm पैकेज अब **`dsh-clinic`** है; `npx dsh-clinic@<version>` और `dsh plugin add dsh-clinic` दोनों इसी की ओर जाते हैं।
- GitHub पर दस रेपो के नाम में `dsh-plugin-doctor` है (आठ बिल्कुल यही नाम), जैसे `zoahdev/dsh-plugin-doctor` (केवल GitHub, कभी npm पर प्रकाशित नहीं)।
- [`dsh-testkit`](https://github.com/PerryLink/dsh-testkit) का README पुराने नाम को zoahdev के रेपो से जोड़ता है; इससे इस रेपो का कोई संबंध नहीं।

एक पंक्ति में: **शून्य-निर्भरता, ऑफ़लाइन सक्षम (`--only R,K`), और कॉर्डिस v4 अनुबंधों (K1–K16) तथा पाँच पारिस्थितिकी डायरेक्टरी सूचियों (CC1–CC5) को ऐसे CI गेट में बदलता है जिसका निर्णय निकास कोड से पढ़ा जाता है।** («एकमात्र» जैसे दावे नहीं — केवल इतना कि जिन उपकरणों की वास्तव में जाँच की गई, उनमें तुलनीय कुछ नहीं मिला।)

## तीन चरणों में शुरुआत

1. **इंस्टॉल करें** (कोई एक चैनल चुनें):

   ```sh
   # git चैनल (नवीनतम main; git+https://github.com/PerryLink/dsh-clinic.git के बराबर)
   dsh plugin --profile web add github:PerryLink/dsh-clinic
   # npm चैनल (प्रकाशित संस्करण)
   dsh plugin --profile web add dsh-clinic
   # tarball चैनल: इस रेपो में pnpm pack के बाद
   dsh plugin --profile web add ./dsh-clinic-<version>.tgz
   ```

   `package.json` में `dsh.bundle.patch` → `cordis.patch.yml` घोषित है, इसलिए यह DSH bundle के रूप में इंस्टॉल होता है और स्वतंत्र CLI (`node doctor.mjs` / `npx dsh-clinic`) के रूप में भी चलता है।

2. **माउंट करें** (bundle रूप एक पंक्ति जोड़ता है; किसी कॉन्फ़िगरेशन कुंजी की आवश्यकता नहीं):

   ```yaml
   - insert:
       - id: plugin-doctor
         name: 'dsh-clinic'
   ```

   जोड़ी गई पंक्ति इस पैकेज को मानक Cordis प्लगइन अनुबंध के तहत लोड करती है: होस्ट आधा एक सादा ESM मॉड्यूल है जो `apply(ctx)` निर्यात करता है (इसका `inject` `tools` और `commands` घोषित करता है)। पैकेज में ब्राउज़र UI नहीं है, इसलिए `dsh.client` घोषणा नहीं है।

3. **जाँचें कि काम कर रहा है**:

   ```sh
   node doctor.mjs --repo . --no-smoke --only R,K
   ```

   ```text
   == 静态·包结构 ==
   [PASS] R0 基础字段（name/version/license/README/type）
       基础字段齐全
   [PASS] R1 激活门 dsh.bundle.patch [关键]
       dsh.bundle.patch = ./cordis.patch.yml
   ```

   **अनइंस्टॉल**: `dsh plugin --profile web remove dsh-clinic` (या प्रोफ़ाइल पैच से वह पंक्ति हटा दें)। CLI उपयोग पर इसका असर नहीं पड़ता।

## मुख्य क्षमताएँ

इन्हीं जाँचों के दो प्रवेश हैं: CLI (`doctor.mjs`, निकास कोड के साथ) और होस्ट आधा (`plugin_doctor` टूल / `/doctor` कमांड, जो पूरी रिपोर्ट लौटाता है)। चार मूल समूह:

- **R | पैकेज संरचना (R0–R8)** — आधार फ़ील्ड; सक्रियण गेट `dsh.bundle.patch` (क्रिटिकल); क्या `npm pack --dry-run` में एंट्री और patch हैं; `cordis.patch.yml` संरचना; एंट्री के `name`/`apply` निर्यात; rescoped निर्भरता नीति; `engines` संरेखण; prebuild + `files` अनुमति-सूची; पुराने rc peer अवशेष।
- **K | कॉर्डिस अनुबंध (K1–K16)** — सेवा पहुँच बनाम `inject` घोषणा; `ctx` लाइव-डेटा सीरियलाइज़ेशन की रेखा; `ctx.effect` में न लिपटे टाइमर/लिसनर; फ़ंक्शन वाला Schema; `apply` का रिटर्न आकार (v4 Effect अनुबंध); `inject` सेवा-नाम seam; v3 के विरासत API; Config Standard Schema होना चाहिए; `name==='apply'` विशेष मामला; K15 नेस्टेड activation spec (होस्ट ≥ 0.2.2-rc.3 ने इसे सपाट किया, इसलिए request के अंदर prompt काम करना बंद कर देता है); K16 थिंकिंग मोड में reasoningEffort के बिना temperature/top_p (चुपचाप अनदेखा, INFO)।
- **D | सैंडबॉक्स स्मोक (D0–D3, D9)** — `npm pack` → `dsh plugin --profile headless add <tarball>` → प्रोफ़ाइल के bundles में पैकेज नाम होने का दावा → `--dump-config` परत-चिह्न → बिना कुंजी वाला headless रन जिसका **exit 1 + `dsh: MISSING_CREDENTIAL`** होना अपेक्षित है (यानी कंपोज़िशन मॉडल अनुरोध तक बूट हुआ) → सैंडबॉक्स सफ़ाई।
- **CC | डायरेक्टरी सूचियाँ (CC1–CC5)** — प्रमाणन रजिस्ट्री spec v1 का पाँच-आयामी evidence; adp-list yml के फ़ील्ड/एनम/विवरण; dsh-catalog प्रविष्टि बाधाएँ (इंस्टॉल कमांड निषिद्ध, truncation heuristic); omdsh `dshWorkshop` सक्रियण के पाँच मान; dsh-plugin-kit के तीन गेट (license / पाँच-भाषा README / तीन seam भूमिकाएँ)।
- **X | होस्ट अनुबंध (पूरक evidence)** — peer corridor, `inject` सेवा-सतह, patch पंक्ति का पता लगना; dsh इंस्टॉल पढ़ने योग्य न हो तो यह समूह degrad होता है और कभी पास होने का नाटक नहीं करता।

**GitHub Action**: रेपो की जड़ में `action.yml` है, इसलिए workflow इसे बिना इंस्टॉल चरण के कॉल कर सकती है: `uses: PerryLink/dsh-clinic@main` (`with: only: R,K`); उत्पादन में किसी प्रकाशित tag पर pin करें।

| `5` | अस्थिर परिणाम (कोई चरण समय-सीमा से बाहर या सिग्नल से मारा गया) | **0.2.0** |
| `6` | **degraded**: माँगा गया समूह वास्तव में कभी नहीं चला (जैसे स्कैन करने के लिए स्रोत फ़ाइलें नहीं) | **0.2.0** |

**मौन उत्तीर्णता के विरुद्ध दो परतें**:

1. `--only` में एक भी समूह-नाम न मिले → तुरंत `2`। 0.1.4 और पहले के संस्करण समूह-नाम के बिगड़ने पर «कुछ नहीं जाँचा + exit 0» करते थे, जिसने एक बार 35 रेपो के CI गेट को झूठा हरा बना दिया (2026-09-09 मापा: `checks_run=0`, `exit=0`)।
2. 0.2.0 से: **माँगे गए समूह की सारी जाँचें skip हों → `6`**। पुराना कार्यान्वयन केवल «एक भी जाँच नहीं चली» को कवर करता था, «चली पर सब skip हो गईं» को नहीं — बाद वाला «K समूह की शून्य कवरेज» को पास मान लेता था। इसे स्पष्ट रूप से स्वीकार करने के लिए `--allow-degraded` दें (exit कोड 0 हो जाता है, पर JSON में `degraded` खाली नहीं रहता)।

> ⚠️ परिवार के मौजूदा 41 रेपो के गेट **exit कोड नहीं पढ़ते** (उनके workflow `set +e` / `out="$(…)"` / `set -e` इस्तेमाल करते हैं) और केवल stdout के `R0 ` / `K1 ` उपसर्ग तथा JSON के `results[].name` पढ़ते हैं। इसलिए 0.2.0 के नए exit कोड **उन पाइपलाइनों के लिए कुछ नहीं बदलते**; वे इंटरैक्टिव उपयोग और भविष्य के इंटीग्रेटर के लिए हैं।

### होस्ट आधा: `plugin_doctor` / `/doctor`

bundle के रूप में इंस्टॉल होने पर प्लगइन वही R/K/X जाँचें केवल-पढ़ने वाले टूल और कमांड के रूप में पंजीकृत करता है। CLI से दो बातें अलग हैं, और दोनों उत्तर में लिखी जाती हैं क्योंकि **होस्ट आधे का कोई exit कोड नहीं होता** — लौटाई गई रिपोर्ट ही पूरा संदेश है:

- **Degraded रन बताते हैं।** जब माँगा गया समूह वास्तव में नहीं चला, तो उत्तर में वही degradation चेतावनी आती है जो CLI छापता है, समूहों के नाम के साथ, ताकि degraded उत्तर को कभी पास न पढ़ा जाए।
- **`workspace` रेपो से हल होता है, इंस्टॉल की जगह से नहीं।** टूल जाँचे जा रहे रेपो से ऊपर की ओर निकटतम ऐसी डायरेक्टरी तक जाता है जिसमें दो या अधिक DSH प्लगइन रेपो हों (`DSH_WORKSPACE` और स्पष्ट पैरामीटर को प्राथमिकता)। 0.7.0 की तरह `import.meta.dirname/..` से हल करने पर bundle रूप में `<profile>/node_modules` (या `…/@perrylink`) मिलता है, जो वर्कस्पेस ही नहीं है: तब CC1–CC4 उन रजिस्ट्रियों के लिए «स्थानीय रूप से नहीं है» बताते हैं जो वास्तव में हैं, और K14 कभी sibling नहीं ढूँढ पाता। वर्कस्पेस न मिलने पर उत्तर यह स्पष्ट कहता है, बजाय उन skip को «रजिस्ट्री अनुपस्थित» जैसा पढ़ने देने के।

पैरामीटर और डिफ़ॉल्ट [कॉन्फ़िगरेशन](#कॉन्फ़िगरेशन) में।

### लक्ष्य आकार और कवरेज

`--repo` एक **स्रोत ट्री** हो सकता है, या **इंस्टॉल किया गया पैकेज डायरेक्टरी / खोला गया tarball आर्टिफ़ैक्ट** (बाद वाला `node_modules/<pkg>` में आम है)। आकार के साथ मानदंड बदलते हैं:

| आकार | K समूह (कॉर्डिस अनुबंध) | टिप्पणियाँ |
|---|---|---|
| `src/` वाला स्रोत ट्री | `src/**` और रूट-स्तर JS स्कैन (`mode: src`) | पूर्ण |
| **`src/` नहीं, `main` `lib/` पर** | **`lib/**` का fallback स्कैन (`mode: lib-fallback`)** | 0.2.0 में ठीक हुआ: पुराना कार्यान्वयन «build स्क्रिप्ट नहीं» पर टिका था, पर प्रकाशित पैकेज अपनी build स्क्रिप्ट **रखते** हैं → fallback कभी नहीं चला, K की नौ जाँचें skip हुईं और फिर भी exit 0 (झूठा हरा) |
| न `src/` न `lib/` | नौनों skip (`mode: none`) | **पूरा समूह वास्तव में नहीं चला → exit कोड 6**, झूठा हरा खत्म |

कवरेज JSON के `coverage.K` (`{filesInspected, mode}`) में लिखी जाती है और `groups.K` में सारांशित होती है।

### `--only` समूह और ASCII उपनाम

| उपनाम | समूह का पूरा नाम | सामग्री |
|---|---|---|
| `R` | स्टैटिक · पैकेज संरचना | R0–R8 |
| `K` | स्टैटिक · कॉर्डिस अनुबंध स्कैन | K1–K16 |
| `D` | डायनामिक · सैंडबॉक्स स्मोक | D0–D3, D9 |
| `CC` | इकोसिस्टम · डायरेक्टरी सूचियाँ | CC1–CC5 |

उपनाम केस-असंवेदी हैं, और चीनी पूरे नाम भी काम करते हैं। **workflow में उपनाम ही इस्तेमाल करें**: यदि एडिटर या स्क्रिप्ट किसी चीनी समूह-नाम को गलत एन्कोडिंग से गुज़ार दे, तो `--only` किसी समूह से नहीं मिलेगा।

### तीन-मान वाला अनुबंध दृश्य (`--format check`)

`--format check` इस प्रोजेक्ट के अधिक समृद्ध envelope की जगह पारिस्थितिकी का सामान्य तीन-मान अनुबंध (`PASS`/`WARN`/`FAIL`, exit `0`/`1`/`2`, सपाट `checks[]`) देता है, ताकि दूसरा परीक्षक या Action परिणाम सीधे उपभोग कर सके। यह एक *दृश्य* है: यह कभी नहीं बदलता कि कोई प्रोजेक्ट पास होता है या नहीं, और `skip` कभी `PASS` के रूप में नहीं दिखाया जाता (वह `skipped: true` के साथ `WARN` बनता है)। पूरी अर्थ-व्यवस्था `doctor` साइड फ़ील्ड में रहती है। देखें `SPEC.md` §1.1 — वे तीन गुण मानक हैं और `tests/compat.mjs` उन्हें जाँचता है।

## सत्यापित बैज

**दो बैज मार्ग** हैं और वे अलग-अलग दावे करते हैं। वह चुनें जिसका दावा आप वास्तव में पूरा कर सकें। **[`FOR-ADOPTERS.md`](FOR-ADOPTERS.md) इस अनुभाग का चरण-दर-चरण संस्करण है** — कौन-सी फ़ाइल कॉपी करनी है, सटीक बैज markdown, हर निर्णय का अर्थ, और यह जाँच क्या *नहीं* साबित करती।

### मार्ग A — स्व-सेवा गेट बैज (कोई अनुमति नहीं, लेखक की भागीदारी नहीं)

यह बैज **एक संकीर्ण, जाँचने योग्य दावा** करता है: *रिपॉज़िटरी अपनी CI में dsh-clinic का स्टैटिक R+K गेट चलाती है, और वह workflow डिफ़ॉल्ट ब्रांच पर हरा है।* यह सीधे आपके workflow की स्थिति से बनता है — GitHub का मूल बैज (दिखाया गया) या shields.io —, इसलिए न रजिस्ट्री प्रविष्टि चाहिए, न PR, न किसी का token, और इसे इस प्रोजेक्ट का इंफ्रास्ट्रक्चर तोड़ नहीं सकता:

```markdown
[![dsh-doctor R+K](https://github.com/<owner>/<name>/actions/workflows/plugin-doctor.yml/badge.svg)](https://github.com/PerryLink/dsh-clinic/blob/main/SPEC.md)
```

`<owner>/<name>` बदलें (और `branch=` भी यदि आपकी डिफ़ॉल्ट ब्रांच `main` नहीं है)। लिंक का लक्ष्य `SPEC.md` है — वे मानदंड जिन्हें आप पूरा करने का दावा कर रहे हैं, और उनके लेखक का स्पष्ट उल्लेख।

**मार्ग A ही इस्तेमाल करें।** यही पूरा मानक है, स्व-सेवा है, और यह विनिर्देश इसी के लिए बना है। इसे इस प्रोजेक्ट से कुछ नहीं चाहिए।

मार्ग A के बारे में दो ईमानदार चेतावनियाँ: बैज *आपके* workflow को दर्शाता है, इसलिए यह उतना ही भरोसेमंद है जितनी आपकी CI कॉन्फ़िगरेशन — कोई और इसे सत्यापित नहीं करता; और यदि आप shields.io रूप इस्तेमाल करें, तो shields.io आपके रेपो का नाम जान जाता है।

### मार्ग B — लेखक द्वारा जारी ऑडिटेड बैज

यह बैज पहनने का अर्थ बिल्कुल एक ऑडिट-योग्य बात है: **रेपो अपनी CI में dsh-clinic का स्टैटिक R+K गेट (23 जाँचें: R0/R1/R3/R5/R6/R7/R8 + K1–K16) चलाता है, और वह गेट डिफ़ॉल्ट ब्रांच के वर्तमान HEAD पर हरा है**, *जिसे इस प्रोजेक्ट के ऑडिटर ने दोबारा जाँचा है*। यह प्रमाणन बैज **नहीं** है: कोई Scorecard नहीं, provenance नहीं, इंस्टॉल स्मोक नहीं। R2 (tarball अखंडता) और R4 (एंट्री अनुबंध) बने हुए `lib/` को पढ़ते हैं, और परिवार के अधिकांश रेपो को बनाने के लिए `HARNESS_COMMIT` + `gen-aliases` चाहिए — वे दोनों हर रेपो के अपने `ci.yml` (build-drift गेट + pack smoke) से कवर होते हैं और जानबूझकर इस गेट से बाहर हैं।

```markdown
[![dsh-doctor](https://raw.githubusercontent.com/PerryLink/dsh-clinic/main/badges/PerryLink__dsh-github.svg)](https://github.com/PerryLink/dsh-clinic/blob/main/README.hi.md#सत्यापित-बैज)
```

**मार्ग B एक केंद्रीकृत, एकल-ऑपरेटर सेवा है और इसे उसी तरह समझना चाहिए।** इसके लिए क्रॉस-रेपो पढ़ने की अनुमति वाला fine-grained PAT चाहिए, जो `DOCTOR_AUDIT_TOKEN` रेपो secret के रूप में रखा जाता है। workflow-स्कोप वाला `GITHUB_TOKEN` इसका **विकल्प नहीं** है: उसमें क्रॉस-रेपो पढ़ने की अनुमति नहीं होती, इसलिए GitHub उसे 60 अनुरोध/घंटा तक सीमित अनाम कॉलर मानता है, जबकि घोषित रेपो का पूरा ऑडिट 200+ चाहता है। PAT के बिना हर बैज ग्रे `NO DATA` दिखाता है — विफलता टूटे बैज प्रोग्राम जैसी दिखती है, गायब secret जैसी नहीं। ऐसा हो चुका है (पहले `401`, फिर `403 rate limit exceeded`), और यही कारण है कि मार्ग A मौजूद है और अनुशंसित है। `scripts/verify.mjs` अब पहली ऐसी प्रतिक्रिया पर रुकता है, `3` से बाहर निकलता है, और ऐसी रजिस्ट्री लिखता है जिसके कारण असली वजह बताते हैं, हर रेपो के लिए वही rate-limit पंक्ति छापने के बजाय।

- रजिस्ट्री `data/verified.json` मार्ग B का एकमात्र सत्य-स्रोत है, जिसे `scripts/verify.mjs` ताज़ा करता है (मूल रूप से रोज़ाना + हर संबंधित push पर workflow चलता था; इस रेपो में अब केवल smoke workflow है, और ताज़ा करने वाली स्क्रिप्ट मौजूद है)। ताज़ा करना केवल GitHub API पढ़ता है: हर रेपो के HEAD `plugin-doctor.yml` गेट कॉन्फ़िगरेशन का विश्लेषण करता है (जिसमें `dsh-clinic@<version>` पिन होना चाहिए, काम करने वाला `--only` तर्क होना चाहिए, और R0/K1 वास्तव में चले हों यह स्व-सत्यापन होना चाहिए), फिर उस HEAD के `plugin-doctor` workflow रन का निष्कर्ष जाँचता है। **इस रेपो की CI कभी तीसरे पक्ष का कोड क्लोन, इंस्टॉल या निष्पादित नहीं करती।**
- बैज रूप: दृश्य भाषा पारिस्थितिकी के दो नए बैजों का अनुसरण करती है (`dsh.directory` का monospace-uppercase + letter-spacing + mark + gradient, और `awesome-dsh-plugin` का seal block) — **चाँदी/प्लेटिनम धात्विक बायाँ खंड, ढाल का tick चिह्न, और स्याही-नीली monospace uppercase**, दायाँ खंड **GitHub-परंपरा का ठोस स्थिति रंग** (हरा/नारंगी/लाल/ग्रे) जिसमें monospace uppercase स्थिति-शब्द है, और स्थिति को **path से बनाया गया आइकन** (✓ / ! / ✕ / –) भी दर्शाता है ताकि रंग-दृष्टि दोष में भी पढ़ा जा सके। 5px कोना त्रिज्या + 1px स्ट्रोक; **स्ट्रोक ज़रूरी है** — उसके बिना चाँदी का बायाँ खंड सफ़ेद README पृष्ठभूमि पर गायब हो जाता है।
- चार अवस्थाएँ (मान-पाठ shields / GitHub Actions के पारंपरिक शब्दों में): `passing` (हरा: HEAD रन सफल) / `warning` (नारंगी: HEAD अभी नहीं चला, रन कतार में है, या गेट पूर्व-शर्त गायब है) / `failing` (लाल: HEAD रन विफल, या गेट कॉन्फ़िगरेशन सही नहीं — जिसमें ऐसा «नकली गेट» भी शामिल है जिसका `--only` तर्क दोहरे एन्कोडिंग से बिगड़ा है) / `no data` (ग्रे: API क्वेरी विफल)। बैज **गतिशील** है: पास होना बंद होते ही लाल हो जाता है। R+K का सटीक दायरा इस अनुभाग और रजिस्ट्री के `meaning` फ़ील्ड में है, बैज पाठ में नहीं (बैज यहाँ वापस लिंक करता है)।
- मार्ग B से जुड़ने के लिए: `data/verified-repos.json` के विरुद्ध PR खोलें और `{ "repo": "<owner>/<name>", "package": "<npm पैकेज नाम>" }` जोड़ें, तथा अपने रेपो में `plugin-doctor.yml` जोड़ें; प्रविष्टि को ऊपर का ऑडिट पास करना होगा। **मार्ग A को इनमें से कुछ नहीं चाहिए।**
- **गेट फ़ाइल वितरित होती है, हाथ से नहीं जोड़ी जाती।** [`plugin-doctor.yml`](plugin-doctor.yml) — आधिकारिक, तैयार workflow — को अपने रेपो के `.github/workflows/plugin-doctor.yml` में कॉपी करें और pin बदलें। यह npm tarball में भी है, इसलिए `npx dsh-clinic` उपयोगकर्ता इस README से चरण दोबारा बनाने के बजाय वितरित प्रति पढ़ सकते हैं। समूह नाम **ASCII उपनाम `R,K`** इस्तेमाल करते हैं (0.1.5 से समर्थित, फ़ाइल और कमांड लाइन दोनों शुद्ध ASCII), और अंत में R0/K1 वास्तव में चले हों यह स्व-सत्यापन होता है।

> गेट क्यों कुछ इंस्टॉल/build नहीं करता, और यह रेपो बैज खुद क्यों नहीं चलाता: स्टैटिक R/K जाँचें केवल कमिट किए गए ट्री को पढ़ती हैं (निर्भरता नहीं चाहिए), जबकि `npm run build` harness aliases के बिना विफल होता है और उसका prebuild कमिट किया गया `lib/` मिटा देता है, जिससे झूठा लाल बनता है। दूसरी ओर तीसरे पक्ष के रेपो की निर्भरताएँ इस रेपो की CI में इंस्टॉल करना सप्लाई-चेन जोखिम होगा। इसलिए गेट हर रेपो की अपनी CI में कमिट किए ट्री के विरुद्ध चलता है, और यह रेपो केवल ऑडिट करके मार्ग B बैज जारी करता है।

## मापे गए आँकड़े

ये संख्याएँ **वास्तविक रन** से हैं, विपणन चार्ट से नहीं। तीसरे पक्ष (गैर-PerryLink) प्लगइनों का पहला स्टैटिक R+K स्कैन (2026-09-10, 0.2.0): **60 उम्मीदवार → 20 प्लगइन जो वास्तव में `dsh.bundle.patch` घोषित करते हैं → 16-जाँच गेट के तहत 10 पास / 10 फेल**। उसी योग्य सेट का 2026-09-23 को 0.3.0 से पुनः स्कैन: **20 उम्मीदवार → 19 योग्य → 6 पास / 13 फेल / 0 degraded / 1 क्लोन विफलता**; गेटेड विफलता हिस्टोग्राम `{"R8":9,"R3":5,"R7":3}`। **R3/R7 सुधारों से कोई रेपो पीछे नहीं हटा** — मुख्य बदलाव पूरा `R8` है: न्यूनतम peer लाइन आगे बढ़ गई, और जो रेपो अब भी `0.1.0-rc.6` पिन करते हैं वे अब मापनीय रूप से पीछे हैं। `R8` को **पुरानापन, टूटना नहीं** पढ़ें। पूरी विधि, प्रति-रेपो तालिका, पुनरुत्पादन कमांड और सुधार चैनल [`THIRD-PARTY-RK-SCAN.md`](THIRD-PARTY-RK-SCAN.md) में; 2026-09-10 का मशीन-पठनीय आधार `data/rk-scans.json` में।

**यह प्रमाणन नहीं, रेटिंग नहीं, और किसी प्लगइन की सुरक्षा के बारे में कुछ नहीं कहता**: पास का अर्थ केवल «उस commit पर 23 स्टैटिक जाँचों ने कोई विफलता नहीं बताई»। विधि: केवल-पढ़ने वाले क्लोन, तीसरे पक्ष के कोड का **शून्य निष्पादन**, R2/R4 अलग सूचीबद्ध और गेट से बाहर; `lib-fallback` कवरेज वास्तविक है पर समतुल्य नहीं, और K3–K7 कम बता सकते हैं। रिपोर्ट में नामित कोई भी रेपो सुधार चैनल से issue खोल सकता है, और पंक्ति दोबारा चलाकर उसी स्थान पर उसी प्रमुखता से सुधारी जाती है।

## कॉन्फ़िगरेशन

`dsh-clinic` का **अपना कोई Config schema नहीं** है — समायोज्य चीज़ें CLI फ़्लैग और होस्ट आधे के छह टूल पैरामीटर हैं। डिफ़ॉल्ट CI के लिए तैयार हैं; ऑफ़लाइन स्टैटिक गेट को केवल `--only R,K --no-smoke` चाहिए।

सामान्य CLI फ़्लैग:

| फ़्लैग | डिफ़ॉल्ट | अर्थ |
|---|---|---|
| `--repo <path>` | आवश्यक | प्लगइन रेपो का पथ (स्रोत ट्री, या इंस्टॉल किया पैकेज डायरेक्टरी / खोला गया tarball आर्टिफ़ैक्ट) |
| `--only <groups>` | सभी | केवल नामित समूह चलाएँ: `R`, `K`, `D`, `CC` (केस-असंवेदी ASCII उपनाम; चीनी पूरे नाम भी काम करते हैं) |
| `--no-smoke` | बंद | डायनामिक सैंडबॉक्स स्मोक छोड़ें; केवल स्टैटिक और सूचियाँ (ऑफ़लाइन/CI स्टैटिक गेट) |
| `--dsh <version>` | peer न्यूनतम | स्मोक का होस्ट संस्करण; डिफ़ॉल्ट npm की नवीनतम प्रकाशित लाइन |
| `--json <path>` | — | रिपोर्ट फ़ाइल में लिखें; `-` का अर्थ stdout (मानव-पठनीय रिपोर्ट दब जाती है) |
| `--format check` | doctor | तीन-मान अनुबंध दृश्य (PASS/WARN/FAIL + 0/1/2, सपाट `checks[]`) |
| `--workspace <root>` | स्वतः | sibling रेपो वाला परिवार वर्कस्पेस (CC1–CC5 और K14 के लिए) |
| `--allow-degraded` | बंद | «पूरा समूह वास्तव में नहीं चला» स्पष्ट रूप से स्वीकारें; डिफ़ॉल्ट exit 6 है |
| `--no-nested-activation` | चालू | K15 बंद करता है (नेस्टेड activation spec) |
| `--no-thinking` | चालू | K16 बंद करता है (थिंकिंग मोड में temperature/top_p का उपयोग) |

<details>
<summary>होस्ट आधे के पैरामीटर (<code>plugin_doctor</code> / <code>/doctor</code>)</summary>

| पैरामीटर | डिफ़ॉल्ट | अर्थ |
|---|---|---|
| `repo` (आवश्यक) | — | प्लगइन रेपो का पथ (`package.json` चाहिए) |
| `smoke` | `false` | D समूह का सैंडबॉक्स स्मोक भी चलाएँ (नेटवर्क + pnpm चाहिए) |
| `host` | `true` | X समूह (होस्ट अनुबंध जाँचें) चलाएँ; dsh इंस्टॉल पढ़ने योग्य न हो तो यह समूह degrad होता है |
| `workspace` | स्वतः | परिवार वर्कस्पेस डायरेक्टरी (कई `dsh-*` प्लगइन रेपो वाला पैरेंट) CC1–CC5 और K14 के लिए; डिफ़ॉल्ट रूप से रेपो से ऊपर की ओर हल होता है, और `DSH_WORKSPACE` भी काम करता है |
| `nestedActivation` | `true` | K15 चलाता है; CLI में `--no-nested-activation` के बराबर |
| `thinking` | `true` | K16 चलाता है; CLI में `--no-thinking` के बराबर |

</details>

पूरी कमांड सतह (`--purge` जैसे रखरखाव फ़्लैग ऊपर की तालिका में नहीं हैं):

```powershell
node doctor.mjs --repo <repo-path>              # पूरा रन (डायनामिक स्मोक सहित; नेटवर्क + pnpm चाहिए)
node doctor.mjs --repo <path> --no-smoke        # केवल स्टैटिक + सूचियाँ
node doctor.mjs --repo <path> --dsh 0.2.2-alpha.3 # स्मोक का होस्ट संस्करण (डिफ़ॉल्ट npm नवीनतम प्रकाशित लाइन)
node doctor.mjs --repo <path> --only R,K        # केवल दो स्टैटिक परतें (ASCII उपनाम अनुशंसित)
node doctor.mjs --repo <path> --json report.json
node doctor.mjs --repo <path> --json -          # JSON stdout पर (मानव-पठनीय रिपोर्ट दब जाती है)
node doctor.mjs --repo <path> --format check --json -   # तीन-मान अनुबंध दृश्य (PASS/WARN/FAIL + 0/1/2)
node doctor.mjs --repo <path> --workspace <workspace-root>   # sibling रेपो वाला वर्कस्पेस (CC समूह उपयोग करता है)
node doctor.mjs --repo <path> --allow-degraded  # «पूरा समूह वास्तव में नहीं चला» स्पष्ट स्वीकारें (डिफ़ॉल्ट exit 6)
node doctor.mjs --purge <quarantine-dir>        # इस टूल द्वारा बनाई गई क्वारंटीन डायरेक्टरियाँ साफ़ करें (केवल doctor-quarantine-*)
```

## FAQ

<details>
<summary>क्या यह मेरे रेपो या वातावरण को छूता है?</summary>

नहीं। स्टैटिक R/K/CC केवल कमिट किए ट्री को पढ़ते हैं: कोई निर्भरता इंस्टॉल नहीं, परीक्षणाधीन कोड का निष्पादन नहीं; तीसरे पक्ष का स्कैन केवल-पढ़ने वाला क्लोन है। D समूह अपना अस्थायी `DSH_HOME`/`DSH_AGENTS_HOME` `%TEMP%` के अपने सैंडबॉक्स में रखता है (उपसर्ग `doctor-`, जो होस्ट-संरक्षित `%TEMP%\dsh-*` टेम्पलेट से **मेल नहीं खाता**), और `dsh plugin add` को हमेशा `--ignore-scripts` दिया जाता है, इसलिए परीक्षणाधीन पैकेज के install/prepare स्क्रिप्ट होस्ट पर कभी नहीं चलते। अंत में रन **मिटाता नहीं, क्वारंटीन करता है** (`%TEMP%\doctor-quarantine-*` में rename), रिपोर्ट के अंत में वह पथ छापता है, और हटाना मानव पुष्टि के बाद `--purge` के लिए छोड़ता है। रन के दौरान दिखे निरपेक्ष पथ JSON या रेंडर किए टेक्स्ट तक पहुँचने से पहले `<path>` में बदल दिए जाते हैं।

</details>

<details>
<summary>क्या PASS प्रमाणन या सुरक्षा रेटिंग है?</summary>

नहीं। पास का अर्थ केवल यह है कि «माँगी गई स्टैटिक जाँचों ने उस commit पर कोई विफलता नहीं बताई»। K समूह **heuristic स्टैटिक स्कैन** है: जटिल wrappers छूट सकते हैं और झूठे अलार्म भी संभव हैं; D3 केवल साबित करता है कि कंपोज़िशन मॉडल अनुरोध तक बूट होता है, यह नहीं कि टूल schema मान्य हैं या बिज़नेस लॉजिक सही है; `R8` विफलता को «पुरानी peer लाइन» पढ़ें, «टूटा प्लगइन» नहीं। यह टूल सुरक्षा ऑडिट नहीं करता, और `dsh.standards` ब्लॉक `not-run` प्लेसहोल्डर है, पास नहीं।

</details>

<details>
<summary>CI में कैसे चलाऊँ? नेटवर्क चाहिए?</summary>

स्टैटिक गेट को नेटवर्क नहीं चाहिए: `npx --yes dsh-clinic@0.8.1 --repo . --no-smoke --only "R,K"`, फिर exit कोड या JSON पर शाखा करें। केवल D समूह के स्मोक को नेटवर्क और pnpm चाहिए। पूरी क्रिया [`plugin-doctor.yml`](plugin-doctor.yml) में है: वह केवल कमिट किया ट्री पढ़ती है, R0/K1 वास्तव में चले हों यह स्व-सत्यापित करती है, और R2/R4 को अलग सूचीबद्ध करती है, उन पर गेट नहीं लगाती (वे बने आर्टिफ़ैक्ट पढ़ते हैं)।

</details>

<details>
<summary>क्या degraded या skip रन झूठा हरा बना सकता है?</summary>

नहीं। `--only` में न मिलने वाला समूह नाम → तुरंत exit 2; माँगा गया समूह वास्तव में न चला → exit 6; `--format check` में skip कभी `PASS` के रूप में नहीं दिखता (`skipped: true` के साथ `WARN` बनता है)। यदि आप सचमुच degradation स्वीकार करना चाहें, `--allow-degraded` दें — exit कोड 0 हो जाता है, पर JSON का `degraded` खाली नहीं रहता और होस्ट आधा उत्तर में समूहों के नाम बता देता है।

</details>

<details>
<summary>npm पर अब भी dsh-plugin-doctor क्यों है?</summary>

## सुरक्षा सीमाएँ

- **स्टैटिक और केवल-पढ़ने वाला।** R/K/CC और तीसरे पक्ष का स्कैन केवल फ़ाइल सिस्टम पढ़ते हैं; परीक्षणों के बाहर परीक्षणाधीन रेपो में कुछ नहीं लिखा जाता। एकमात्र लेखन इस टूल का अपना `%TEMP%` सैंडबॉक्स और क्वारंटीन डायरेक्टरियाँ हैं।
- **एक बार का सैंडबॉक्स।** D समूह का अस्थायी `DSH_HOME`/`DSH_AGENTS_HOME` `%TEMP%\doctor-*` में रहता है और असली `~/.dsh` को कभी नहीं छूता (लाल रेखा 3)।
- **परीक्षणाधीन पैकेज की इंस्टॉल स्क्रिप्ट नहीं।** `dsh plugin add` स्पष्ट रूप से `--ignore-scripts` देता है; pnpm का `ignored-builds` ब्लॉक `environment` के रूप में वर्गीकृत होता है (न पास गिना जाता, न प्लगइन दोष)।
- **क्वारंटीन, मिटाना नहीं।** हर चरण का subprocess stdout/stderr `%TEMP%\doctor-run-*\logs\` में लिखा जाता; अंत में रन उसे `%TEMP%\doctor-quarantine-*` में rename करता है, रिपोर्ट के अंत में वह पथ छापता है, और हटाना मानव पुष्टि के बाद `--purge` पर छोड़ता है (लाल रेखा 4, तीन-चरण नियम)।
- **पथ redaction।** रन में दिखे निरपेक्ष पथ JSON या रेंडर किए टेक्स्ट में जाने से पहले `<path>` बन जाते हैं, इसलिए रिपोर्ट किसी और के रेपो में commit की जा सकती है बिना उसके path-leak गेट को ट्रिगर किए।
- **बंद-विफलता, झूठा हरा नहीं।** अज्ञात समूह/अज्ञात विकल्प → 2; पूरा समूह कभी न चला → 6; degradation स्पष्ट रूप से `--allow-degraded` से स्वीकारनी होगी; `skip` कभी `pass` नहीं लिखा जाता।

## ज्ञात सीमाएँ

- K समूह **heuristic स्टैटिक स्कैन** है: K1/K3/K4 जटिल wrappers चूक जाते हैं और झूठे अलार्म भी दे सकते हैं — warn-स्तर का हर निष्कर्ष मानवीय नज़र माँगता है और किसी प्लगइन को अपने आप दोषी नहीं ठहराता।
- D3 केवल यह साबित करता है कि «कंपोज़िशन मॉडल अनुरोध तक बूट होता है»; यह **नहीं** साबित करता कि टूल schema मान्य हैं या बिज़नेस लॉजिक सही है (उसके लिए कुंजी वाला e2e रन या mock LLM चाहिए)।
- pnpm `ignored-builds` पर्यावरण-विधि की समस्या है: जब D1 इसे भेटता है, जाँच warn में degrad होती है और `compat.yml` की `allowBuilds` विधि छापती है, जो प्रमाणन spec v1 की environment-blocked पंक्ति से मेल खाती है, और इसे कभी प्लगइन दोष नहीं गिना जाता।
- npm लाइन के होस्ट (0.1.2-rc.1) के packument में engines/peerDependencies प्रवर्तन नहीं है, इसलिए वहाँ R6 केवल सलाहकारी है।
- इस वातावरण में मापा गया एक जाल: `$` एंकर (`m` फ़्लैग के बिना) अकेले अंतिम `\r` से पहले की स्थिति से मेल नहीं खाता, इसलिए CRLF टेक्स्ट पार्स करते समय `/\r?\n/` पर विभाजन ज़रूरी है (आंतरिक रूप से पहले से संभाला गया — इसे वापस न करें)।
- **मानक क्रॉसवॉक।** R/K/D — X पूरक evidence के साथ — केवल **DSH-ENTRY** संगतता आधार-रेखा पर मैप होते हैं; JSON envelope में अब additive `standards` फ़ील्ड (`dsh-levels/1`) है। DSH-FLOW (`J1–J8`) `manual` है और DSH-BOOST (`LEV-1..LEV-8`) `not-measured` — यह टूल कोई उपयोगकर्ता-यात्रा या benchmark नहीं चलाता — और ये स्तर आधिकारिक DeepSeek मानक नहीं हैं। देखें [`STANDARDS.md`](STANDARDS.md) और `data/standards.json`।

### रिलीज़ स्वास्थ्य

हरा release workflow सही रिलीज़ साबित नहीं करता। 2026-10-05 को परिवार ने 37 पैकेज भेजे और जो विफलताएँ मायने रखती थीं वे job के रंग में अदृश्य थीं: 36 CHANGELOG में अक्षरशः तारीख `undefined` थी, दो पैकेज सफलतापूर्वक प्रकाशित हुए और फिर भी लाल रहे, एक `ENEEDAUTH` से विफल हुआ क्योंकि npm का trusted-publisher binding ऐसी workflow फ़ाइल नाम दे रहा था जो अब OIDC एक्सचेंज नहीं करती, और एक npm तक पहुँचा ही नहीं क्योंकि उसका प्रकाशन-पूर्व `verify` गेट पहले विफल हुआ और publish job `skipped` रह गया।

`scripts/check-release-health.mjs` उन सबको कवर करने वाली चार चीज़ें जाँचता है:

| Pass | प्रश्न | नेटवर्क चाहिए? |
|---|---|---|
| LOCKSTEP | क्या रेपो का हर संस्करण-वाहक `package.json` से सहमत है? | नहीं |
| PUBLISHED | क्या स्थानीय संस्करण वही है जो रजिस्ट्री पर है? | हाँ |
| PROVENANCE | किस workflow फ़ाइल ने प्रकाशित किया, और क्या वह वर्तमान प्रकाशन फ़ाइल है? | हाँ |
| FILES | क्या प्रकाशित tarball में अब भी `src/`, `lib/` या `dist/` है? | हाँ |

```sh
# एक रेपो, ऑफ़लाइन (डाउनस्ट्रीम रेपो को अपनी CI में यही मोड इस्तेमाल करना चाहिए)
node scripts/check-release-health.mjs --repo . --no-registry

# पूरा घोषित परिवार, रजिस्ट्री से, कुछ भी checkout किए बिना
node scripts/check-release-health.mjs --roster data/verified-repos.json
```

निकास कोड: `0` स्वस्थ, `1` कम से कम एक समस्या, `2` उपयोग त्रुटि। `--json <path>` मशीन-पठनीय रिपोर्ट लिखता है, `--quiet` केवल विफलताएँ छापता है। दोनों कमांड आपकी अपनी CI में जोड़े जा सकते हैं।

केवल दो वाहक आकार जाँच विफल करते हैं, क्योंकि पूरे परिवार में केवल दो पर दावा किया जाता है: `src/version.ts` का निर्यातित `VERSION`, और जहाँ हो वहाँ `VERSION` फ़ाइल। `SKILL.md` का संस्करण अंतर note के रूप में रिपोर्ट होता है — अधिकांश skill स्वतंत्र रूप से संस्करणित होते हैं।
